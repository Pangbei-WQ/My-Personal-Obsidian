## 一句话总结

**VibeCoding 不是某个具体工具，而是 AI 编程两年演化的"顶层形态"**——它的底层结构只有三层：**AI 大模型（生成内容）→ Agent（代替人执行命令）→ 工作流（让过程稳定）**。无论工具名一年换三茬（Claude Code、Codex、OpenCode、OpenSpec、Superpowers……），这套结构不变；理解了它，任何新概念都能定位到"这是在哪一层解决什么问题"。

---

## 核心结构总览

| 层 | 角色 | 解决什么问题 | 代表物 |
|----|------|------------|--------|
| **第 1 层：AI 大模型** | 生成内容的大脑 | "谁负责想" | Claude / GPT / 通义千问 / DeepSeek 等 |
| **第 2 层：Agent** | 长在用户电脑上的手 | "谁负责做" | Claude Code、Codex、Cursor、Copilot、OpenCode 等 |
| **第 3 层：工作流** | 固定流程的规章制度 | "怎么做得稳" | OpenSpec（SDD）、Superpowers（TDD）、linter、hooks 等 |

## 主体内容

### 1. 一层一层拆：名字再多，结构只有三层

视频开篇抛出一堆让人晕的名词——Claude Code、GPT、Codex、OpenCode、Superpowers、OpenSpec……然后逐一归位：

#### 第 1 层：AI 大模型（负责"生成"）

- 我们最早认识的 AI 是**聊天界面**：发一段文字，回一段文字。但聊天网站本身没有智能，它只是把消息转发给背后的**大语言模型（LLM）**，由模型生成回复。
- 常说的 Claude / GPT / 通义千问 / DeepSeek，最初指的就是背后的大模型；后来人们也用它指代"网站+模型"这个整体。
- 各家卷出不同特点：
  - **GPT**：着重多模态，想支持一切场景。
  - **Gemini**：忙着与 Google 自家产品互动。
  - **国产模型**（千问、DeepSeek 等）：受芯片/算力政策限制，更注重模型本身的**效率和架构创新**。
  - **Claude（Anthropic）**：比较特殊——别的模型能写歌、画图、生成 AI 小电影，Claude 全都不会，但它**把写代码这个功能卷到了世界第一**。所以哪怕价格已经"快要上天"，写程序依然首选 Claude。
- Claude 的版本：圈内常说的 **Sonnet、Opus** 等（转录中另有两个代号「misss」「feable」，疑为 ASR 误差，待核实），区别是模型复杂程度与价格不同——类比手机分普通版 / Pro / Pro Max / "年度典藏导演剪辑版"。

#### 第 2 层：Agent（负责"执行"）

- **痛点**：网页聊天室沟通太困难——AI 每输出一段代码都要手工复制到本地运行，报错再粘回去，写个小程序要来回几十次。
- **为什么 AI 不能直接操作我们的电脑？**
  1. 模型和聊天界面都跑在**厂商的服务器**上，与我们本地电脑是两台机器，无法直接访问本地硬盘。
  2. 模型唯一的能力就是"根据输入思考并产出一段内容"（文字、图片、歌……），**单靠产出内容无法与环境互动**——"我要读 main.py"，文件不会自己跑到模型面前。
- **Agent = 跑在用户电脑上的程序**，相当于给 AI 配了一只可远程操控本地电脑的手：
  - 能访问本地文件；
  - 执行 AI 的指令（如"读 main.py""在第七行加入 print"）；
  - 把执行结果返回给 AI。
- 对话变成：**用户 → Agent → AI → Agent → 用户** 的循环。
- **Function Calling**：AI 会回复一种特殊格式（一般是 JSON 字符串），Agent 靠识别它来区分"这是一条指令"还是"要显示给用户的文字"。
- 常见 Agent：
  - **模型厂商自研**：Anthropic 的 **Claude Code**、OpenAI 的 **Codex**、谷歌的 CLI 编程工具（转录作「ant gravity」，待核实）；
  - **第三方**：**Cursor、Copilot**，以及开源 **OpenCode** 等。
- Agent 与模型是**两套独立体系，可自由搭配**：如用 OpenCode 当 Agent、底下接 Claude；国内因网络/价格限制，很多人用 Claude Code 或 Codex 搭配国产模型。

#### VibeCoding 的命名

- OpenAI 联合创始人 **Andrej Karpathy** 在 **2025 年初**给这种"只管提需求、对 AI 写出的代码看都不看、全凭感觉"的编程方式起了名字：**Vibe Coding**。
- 之后人们对"Agent + 模型"这套组合针对 Vibe Coding 做了大量优化。

### 2. 现实问题：AI 写程序并不美好

- **目光短浅**：改好一个 bug，却引入新 bug，甚至破坏原有逻辑。
- **需求不明确**：让 AI 做个《塞尔达》，它做出了《原神》。（不过多数情况是我们自己没把话说清楚。）
- 于是人们发明了一堆**和 AI 沟通的技巧**：

| 技巧 | 做法 | 缩写 |
|------|------|------|
| 先讨论需求 | 写程序前先与 AI 讨论，通过不断提问整理答案，明确到底想要什么 | — |
| 规范文档驱动 | 先写规范文档，再按文档开发 | **SDD** |
| 测试驱动 | 先写测试用例，把写程序变成"不断让测试通过" | **TDD** |
| 静态检查 | 写完必须调用各类静态检查器，全部通过才算完成 | — |

- **副作用**：本来一句话就能让 AI 写程序，现在又是定需求又是 SDD 又是 TDD，一套流程下来字数够写一篇高考作文——太麻烦。

### 3. 工作流：把提示词变成模板和规则

- 人们自然想到：**把辛苦写出来的提示词变成模板，分享给所有人用**。GitHub 上有很多这类工程，流行的两个：
  - **OpenSpec**（走 SDD 流程）：先讨论 → 写需求和规范 → 最后写代码。
  - **Superpowers**（走 TDD 流程）：先讨论 → 写需求和测试 → 最后写代码。
- 它们大多用到 Agent 内置的**提示词模板**功能。例：在支持的 Agent 里输入 `open spec explore，我想实现一个塞尔达`，就相当于输入了一篇几千字的小作文，AI 会通过提问逐步理清需求；再输 `open spec propose`，把讨论结果转化成文档；最后输 `open spec apply`，把文档转成代码。Superpowers 用法类似、命令不同。
- 除提示词模板外，还常带**小程序 / 规则文件**限制 AI 行为：确保格式正确的 **linter**、防止文档定稿后被 AI 乱改的 **hooks** 等。
- **工作流 = 这一整套（提示词模板 + 小程序 + 规则文件）把 AI 的开发过程变成固定顺序。**

### 4. 两年演化的主线

| 阶段 | 形态 | 痛点→解法 |
|------|------|----------|
| 早期 | 聊天窗口复制粘贴、手工运行 | 来回几十次太痛苦 |
| 中期 | Agent 代替用户自动执行命令 | AI 无法直接操作电脑 → 程序代理 |
| 现在 | 工作流让 Agent+模型更稳定 | 提示词太长 → 模板化 + 规则化 |

> 未来也许编程真的就是和 AI 说一句"我想写个塞尔达"。
> 作者核心观点：**工具一年换三茬，底下这套结构（模型→Agent→工作流）是不变的**。再火的东西也不过是同一个老故事加了点佐料、起了个新名字。化用《庄子·齐物论》"枢始得其环中，以应无穷"——掌握了枢纽（底层结构），就能以不变应万变。（转录原文作"书使得其还中，已应无穷"，系 ASR 误差。）

## 要点提炼

1. **三层定位法**：遇到任何 AI 编程新词，先问它属于哪一层——模型层（谁在思考）、Agent 层（谁在执行）、工作流层（怎么保证稳定）——立刻就不慌了。
2. **模型与 Agent 解耦**：二者没有绑定关系，可随意搭配，这是生态如此繁荣的原因。
3. **Claude 的定位**：Claude 在"写代码"这一件事上做到世界第一，是编程场景首选；其余多模态能力并非其长项。
4. **工作流本质是"工程化"**：Vibe Coding 之所以从"一句提示词"走向"SDD/TDD/模板/linter/hooks"，是因为**裸 AI 不够可靠，需要把过程变成固定、可审计的顺序**。
5. **以不变应万变**：底层结构短期不会变，学习应聚焦结构而非追新名词。
